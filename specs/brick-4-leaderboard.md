# Brick 4 — Public leaderboard

**Goal:** flip VANTAGE from "contestant who happens to win the benchmark in their README" to "the referee that defines the benchmark." Publish the harness, the ground-truth catalogs, and a weekly-updated public ranking. Force every competitor to either show up and lose or refuse to show up.

**Why this brick is cheap and high-leverage:** the harness already exists in the `benchmarks/` folder. The ground-truth catalogs already exist. The work is mostly extraction, polish, and a static site — not new technology. But it permanently changes how every conversation about static analysis happens, because once there's a public leaderboard, "what's your score on the JourdanLabs benchmark?" becomes the question.

**Success criteria:**
- A public site at `benchmark.vantage.dev` (or similar) listing every static analysis tool ranked by F1 + speed on a standardized corpus.
- The full harness open-sourced under a permissive license (MIT) so any tool can self-submit.
- Ground-truth catalogs published under CC-BY so they can be cited and reused.
- A GitHub Actions workflow that runs the full benchmark weekly and updates the site automatically.
- VANTAGE listed honestly alongside Semgrep, SonarQube, CodeQL, Snyk Code, and any others that submit.

## Sub-spec 1: Extract the harness

The current `benchmarks/` directory has the methodology and per-finding breakdowns embedded in a markdown report. The first job is to lift the harness logic out into a standalone, reusable Node/TS package.

### Deliverable

A package `vantage-bench` that can run any static analysis tool against the corpus and produce comparable metrics.

### Files to create

```
packages/vantage-bench/
├── src/
│   ├── corpus.ts              # Loads OWASP NodeGoat, Juice Shop, future corpora
│   ├── runners/
│   │   ├── vantage.ts         # Runs vantage, parses JSON
│   │   ├── semgrep.ts         # Runs semgrep, normalizes findings
│   │   ├── sonarqube.ts       # Runs sonar, normalizes findings
│   │   ├── codeql.ts          # Runs codeql via CLI, normalizes
│   │   └── base.ts            # Abstract runner interface
│   ├── ground-truth/
│   │   ├── nodegoat.json      # Lifted from benchmarks/
│   │   ├── juice-shop.json    # Lifted from benchmarks/
│   │   └── schema.ts          # Ground truth shape
│   ├── scoring.ts             # Precision, recall, F1, runtime
│   └── report.ts              # Markdown + JSON output
├── bin/
│   └── vantage-bench.js       # CLI entrypoint
└── README.md                  # How to run, how to add a tool
```

### Runner interface

Every tool runner implements:

```typescript
interface Runner {
  name: string;
  version: string;
  run(targetPath: string): Promise<{
    findings: Finding[];
    durationMs: number;
  }>;
}

interface Finding {
  file: string;
  line: number;
  type: string;
  severity: 'CRITICAL' | 'HIGH' | 'MED' | 'LOW';
  description: string;
}
```

A new tool joins the leaderboard by submitting a PR adding a runner. This is the contribution surface that makes the leaderboard self-sustaining.

### Ground truth schema

```typescript
interface GroundTruth {
  corpus: string;
  vulnerabilities: Array<{
    id: string;
    file: string;
    line: number;
    type: string;
    cve?: string;
    description: string;
  }>;
}
```

A finding from a tool is a true positive if its `file` matches and its `line` is within ±5 of a ground-truth entry of the same `type`. Otherwise false positive. Ground-truth entries with no matching finding are false negatives.

## Sub-spec 2: The leaderboard site

### Deliverable

A static site (Astro or Next.js static export — pick whichever you prefer; spec assumes Astro for simplicity) hosted at `benchmark.vantage.dev`.

### Pages

`/` — main leaderboard. Sortable table: tool, version, NodeGoat F1, Juice Shop F1, runtime (ms), date last run. Default sort by aggregate F1 descending.

`/tools/<tool>` — per-tool detail page. Per-corpus breakdown, false positive list, false negative list, runtime distribution.

`/methodology` — published methodology. Same content as the current `BENCHMARK_REPORT.md` but presented as authoritative reference.

`/submit` — instructions for submitting a new tool. Just a link to the GitHub repo and the runner contract.

### Files to create

```
sites/leaderboard/
├── src/
│   ├── pages/
│   │   ├── index.astro
│   │   ├── tools/[tool].astro
│   │   ├── methodology.astro
│   │   └── submit.astro
│   ├── components/
│   │   ├── LeaderboardTable.astro
│   │   └── FindingsList.astro
│   └── data/
│       └── results.json       # Generated by the weekly workflow
├── astro.config.mjs
└── package.json
```

The site reads `results.json` at build time. The weekly workflow regenerates `results.json` and triggers a rebuild.

### Hosting

Cloudflare Pages or Vercel. Cheap, fast, automatic deploys on push.

## Sub-spec 3: Weekly automation

### Deliverable

A GitHub Actions workflow that runs the full benchmark suite weekly, updates `results.json`, and triggers a site redeploy.

### Files to create

```
.github/workflows/
├── benchmark-weekly.yml       # Runs Sunday 02:00 UTC
└── benchmark-on-pr.yml        # Runs on PRs that touch packages/vantage-bench
```

The weekly workflow installs every supported tool, runs the harness, commits `sites/leaderboard/src/data/results.json` to `main`. The Cloudflare/Vercel project picks up the commit and redeploys.

### Reproducibility

Every result includes a `commit_sha` of `vantage-bench` and the version string of the tool that produced it. Anyone should be able to reproduce a result by checking out the listed `commit_sha` and running `vantage-bench run --tool <name>` locally. This is the credibility moat — opaque benchmarks are easy to dismiss.

## Sub-spec 4: Launch coordination

### Deliverable

A coordinated launch that gets the leaderboard noticed without looking like a stunt.

### Steps

Pre-launch: invite Semgrep, SonarSource, GitHub (CodeQL), and Snyk maintainers to review the methodology in private 2 weeks before launch. Address legitimate critiques. The goal is not to ambush — it's to be irrefutable when you do go live.

Launch post: a single technical blog post on the JourdanLabs site walking through the methodology, showing the current rankings, and explicitly inviting submissions. Tone is matter-of-fact, not triumphant. Let the numbers do the work.

Distribution: HN, /r/programming, /r/netsec, post on LinkedIn from the company account. Don't post from a personal account that looks like astroturfing.

Follow-up: respond to every legitimate methodology critique publicly in GitHub issues. Update the harness if the critique is valid. The leaderboard's credibility compounds with every disputed-but-resolved issue, not with every silenced one.

## Sequencing within Brick 4

Harness extraction first (3–4 days). Site second (2–3 days, mostly because design polish takes longer than you expect). Weekly workflow third (1 day). Then 2 weeks of pre-launch outreach, then launch.

Realistic timeline: 2 weeks of build, 2 weeks of pre-launch quiet period, then live. Total ~30 days from green-light to public launch.

## Open questions

Should the leaderboard include commercial tools that require a license to run (Snyk Code, Veracode)? Pro: completeness. Con: someone has to pay for the licenses to keep results current. Suggest: include them with a note that "results last updated on <date>" and let the vendors submit their own runs if they want fresher numbers.

Do you want a hosted "submit your repo, get a verdict" surface on the site, or keep it strictly to fixed corpora? Hosted submission would massively expand the data flywheel but also creates abuse and cost surface. Suggest: not in v1; revisit after the leaderboard is established.

What's the relationship between the leaderboard and a future paid VANTAGE Cloud product? Free leaderboard drives awareness; paid product is the upsell. Be careful not to conflate them in the launch narrative — leaderboard launches first, alone, with no upsell pitch.
